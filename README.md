# 订单 / 支付双表日粒度实收对账

用 `reconcile.py` 对 `data/orders.csv`（订单状态记录）与 `data/payments.csv`（支付流水）
分别算日粒度实收 GMV 与日环比，再按 (北京自然日, 订单号) 对账，输出两套日粒度结果、
差异明细与汇总报告。

## 运行

```bash
python3 reconcile.py                       # 默认读 data/，结果写到仓库根目录
python3 reconcile.py --out-dir out         # 指定输出目录
python3 -m pytest test_reconcile.py -q     # 跑测试
ruff check reconcile.py test_reconcile.py  # 静态检查
```

环境只依赖 Python 3 + pandas（样例在 Python 3.12 / pandas 3.1 下验证）。

## 产出

| 文件 | 内容 |
|---|---|
| `orders_daily.csv` | 订单口径每日 `gmv`、`prev_gmv`、`mom_pct`（环比百分比） |
| `payments_daily.csv` | 支付口径每日 `gmv`、`prev_gmv`、`mom_pct` |
| `diff.csv` | 每个对不上的 (日, 订单)：两侧金额、差异金额、归因分类与说明 |
| `summary.txt` | 两边口径总额、差异总额、四类各自的笔数 / 净额 / 绝对额 |

两侧日表都按完整日历日补齐（缺失日记 0），因此行数与窗口天数一致、可直接并排比较。
`mom_pct = (当日 / 前一日 - 1) * 100`；首日与"前一日为 0"的情形留空，避免除零产生
无意义的环比。

## 口径

**时间统一到北京时间。** 订单表的 `updated_at` 是运营系统落库的北京时间（无时区标记），
直接使用；支付表的 `paid_at` 是 UTC，先 `tz_convert("Asia/Shanghai")` 再取自然日。
这一步是全流程的关键：约 16/700 笔支付换算后会跨到次日的北京时间自然日，
另外 UTC 与北京时间本身相差 8 小时，若不换算会导致整日错位。

**订单终态按状态机定，不按时间序。** 同一 `order_id` 可能有多行（下单 / 改价 / 成交 / 取消），
且 `updated_at` 偶有乱序（例如"成交"之后才落"下单"行）。终态取优先级最高者：

```
成交(4) > 改价(3) > 下单(2) > 取消(1)
```

同优先级取 `updated_at` 最新的一行；时间戳相同取文件中靠后的一行，保证结果可重复。
实测若改用"时间戳最新"作终态，会有 18 个订单结论被乱序行带偏（如已成交的单被
晚落的"取消"行清成 0）。

**实收 = 订单终态净额（财务口径）。** 取消终态计 0；改价终态按改价行的金额；
金额为负表示退款 / 冲抵，参与净额累加。支付侧按 `order_id` 汇总所有流水，
同一订单拆成多笔支付时求和（若一笔订单跨两个自然日支付，按实际支付日分别入账）。

**差异 = 订单口径 − 支付口径。** 最小值单元是 (北京日, 订单号)；同日同单归一行为一行差异，
使每行只落一个分类。

## 差异归因（四类互斥，每行恰好一类）

判定顺序即优先级，先命中先归类：

1. **时区窗口差** — 订单与支付金额一致，但支付换算北京时间后落在相邻自然日。
   同一笔钱在两日各记一次，跨日净额相互抵消（故该类别净额为 0），但按日看两侧仍错位。
2. **退款或负向冲抵** — 终态为取消但支付表仍有收款；或订单 / 支付任一侧出现负金额
   （退款、冲抵、负向调整）。
3. **重复或多状态行** — 订单有多行状态记录导致终态金额与支付口径不一致；或同一订单
   拆成多笔支付、金额无法逐笔对齐。
4. **其余未对上** — 单边缺失（有单无款 / 有款无单）等无法归入前三类的差异。

分类依据订单级上下文（订单是否存在、有几行、支付有几笔、是否含负数），因此跨日的那对
差异行会拿到同一个分类，不会一半判"时区"一半判"其余"。

## 样例数据结果

窗口 2026-10-01 ~ 2026-10-30（30 天，北京时间），订单 800 行 / 605 个终态订单，
支付 700 笔 / 569 个订单：

| 项 | 金额 |
|---|---|
| 订单口径实收 GMV | 152,059.41 |
| 支付口径实收 GMV | 157,248.00 |
| 对账差异总额（订单 − 支付） | −5,188.59 |

| 分类 | 笔数 | 差异净额 | 绝对差异 |
|---|---:|---:|---:|
| 时区窗口差 | 32 | 0.00 | 8,464.08 |
| 退款或负向冲抵 | 16 | −4,613.99 | 4,613.99 |
| 重复或多状态行 | 12 | −47.41 | 608.95 |
| 其余未对上 | 12 | −527.19 | 2,873.09 |
| 合计 | 72 | −5,188.59 | 16,560.11 |

差异明细 72 行的净额与两侧总额之差精确相等（脚本内置这项勾稽，不平会直接报错），
日粒度合计与各自总额也逐项校验。四类中退款 / 负向冲抵是主要缺口来源：25 个订单终态
金额为负（其中 13 笔对应支付流水同为负，差异是负值翻倍；另 12 笔支付仍为正，相当于
订单侧按退款冲抵、支付侧仍记正数），另有 4 个终态取消的订单仍留在支付流水里。

## 代码结构

| 函数 | 职责 |
|---|---|
| `load_orders` / `load_payments` | 读表、校验列与枚举、解析金额、统一时间到北京时间 |
| `build_final_orders` | 状态机优先级选终态（乱序 / 多行容错） |
| `_daily_gmv` | 日历补零、日环比 |
| `reconcile` | (日, 订单) 外连接 + 订单级上下文，产出差异行 |
| `_classify_row` | 四类互斥归因与文字说明 |
| `_category_stats` / `_build_summary` | 分类汇总与报表 |
| `run` | 串联流程、执行总额勾稽、写文件 |

错误处理：缺文件 / 缺列 / 金额或时间无法解析 / 状态机外的状态 / 空输入一律抛错退出
（`main` 返回非 0 退出码），并带可定位的示例值；重复 `pay_id`、空表等情况打 WARNING 日志，
不静默吞掉。

## 测试

`test_reconcile.py` 共 25 个用例，覆盖：

- 状态机：优先级压过时间戳、改价压过下单、同状态取最新、输入行乱序结果不变、未知状态报错；
- 时区：UTC 跨零点归到次日北京时间、订单裸时间戳不被二次偏移；
- 日粒度：日历补零、环比取前一日、前一日为 0 时留空；
- 归因：四类各有用例，含"同订单既多笔支付又有负金额"只落一类的互斥校验；
- 勾稽：差异明细净额 = 两侧总额之差、四个输出文件齐全、空输入报错；
- 样例数据端到端回归：总额、30 天窗口、日合计、72 行明细分类封闭性、环比可重算。
